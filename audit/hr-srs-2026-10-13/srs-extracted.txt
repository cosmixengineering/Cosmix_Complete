046: 1 System Purpose and Scope
047: The solution will provide one controlled HR and attendance platform for office employees, site staff, supervisors, HR, Accounts and management. Employees will use the mobile application for check-in, check-out and self-service. Authorized office users will use the React web application for employee administration, shifts, attendance review, policy configuration, approvals, reports and payroll handoff.
048: 1.1 Primary Objectives
049: Maintain a reliable employee master with personal, employment, contact, document, assignment and compensation information.
050: Capture attendance through the mobile application with face verification at Check In and authorized correction without losing original evidence.
051: Apply office and site policies consistently using versioned rules with effective dates.
052: Give each employee secure access to their own attendance, salary summary, deductions, overtime, leave, advance and loan information.
053: Provide traceable approvals and audit history for corrections, overtime, leave, allowances and policy exceptions.
054: Generate verified attendance outputs for Accounts and payroll without allowing Accounts to rewrite original punches.
055: 1.2 Included Scope
056: Authentication, session management, password recovery and role-based access control.
057: Employee master, onboarding, employment history, documents, certifications, emergency details and status lifecycle.
058: Departments, designations, reporting lines, branches, sites, staff categories, shifts, rosters and holidays.
059: Mobile check-in/check-out, face verification at Check In, geolocation evidence, server timestamps and attendance exceptions.
060: In-app site arrival/departure reporting and employee-specific authorized, controlled and restricted operational zones.
061: Office and site attendance rules, overtime, meal allowance eligibility, travel day treatment and attendance corrections.
062: Leave requests, balances, evidence, approval and attendance integration.
063: Employee self-service web/mobile views and supervisor-limited views.
064: Fuel, motorcycle tuning and vehicle custody policy records where they affect employees and payroll claims.
065: Reports, exports, notifications, audit logs and payroll-ready attendance summaries.
066: 1.3 Out of Scope for the First Production Release
067: Automatic salary disbursement to a bank. The first release may generate an approved payroll handoff or bank advice file only.
068: Medical diagnosis or AI-based disciplinary decisions.
069: Unrestricted live tracking outside an authorized attendance or assigned field-work event.
070: Attendance-machine, time-clock or other attendance-hardware integration. The mobile application is the production attendance channel.
071: Final payroll accounting ledger if Accounts chooses to retain it in a separate finance module.

098: 3.1 Logical Request Flow
099: 1. React or React Native sends an authenticated HTTPS request to the ASP.NET Core API.
100: 2. The API validates the access token, role, employee/site scope and request schema.
101: 3. The application service loads effective policy, shift, roster and assignment data for the event date.
102: 4. The domain service calculates or validates the result and records source evidence, result and audit metadata in one transaction.
103: 5. Notifications and noncritical processing run through background jobs after the transaction commits.
104: 3.2 Environments
105: Development, Test/UAT and Production must use separate databases, storage, secrets and API endpoints.
106: Production secrets must be stored in a secure secret manager or protected server configuration, never in React or React Native source code.
107: Demo/mock data must never be mixed with production employee records.

207: 7 Attendance Processing
208: Attendance must preserve evidence in two layers. Raw Punch Events store every received check-in/out event unchanged. Daily Attendance Summaries derive work time, status, late minutes, overtime and policy effects. A correction changes the interpreted summary or adds an authorized adjustment; it must not delete the original punch.
209: 7.1 Attendance Sources
210: Source | Required Evidence and Handling
211: Employee mobile app | Employee, device, server timestamp, claimed action, Check-In face-verification result/token, coordinates, accuracy, site, optional attachment and online/offline state.
212: In-app site report | Employee, assigned site/task, arrival/departure or incident type, server/device time, coordinates, notes, attachment, submission status and reviewer.
213: File import | Source file hash, importer, mapping, duplicate report, validation errors and import batch.
214: Authorized manual entry | Employee, time, reason, evidence, requester, approver and original/corrected values.
215: 7.2 Mobile Check In and Check Out Flow
216: 1. Employee signs in and the app loads the current assignment, shift and attendance state from the API.
217: 2. For Check In, the app starts a live face challenge and requests location permission for the attendance event. Check Out does not require face verification.
218: 3. The app confirms liveness and a one-to-one match against the signed-in employee's active face enrollment, then obtains a short-lived verification result/token.
219: 4. The app captures coordinates, accuracy, device time and device identifier, then sends the event and required verification result over HTTPS.
220: 5. The server uses its own receipt time as the authoritative time and validates assignment, duplicate state, allowed time window and configurable geofence.
221: 6. The server stores the raw event, returns accepted, accepted with exception, queued for review or rejected with a clear reason.
222: 7. The app displays the server-confirmed time, location/site and attendance status. A locally displayed success without server confirmation is not a valid punch.

245: 7.3 Attendance Correction
246: 1. Employee or authorized supervisor submits the correction with requested time/status, reason and evidence.
247: 2. HR or the configured authority reviews source punches, assignment, shift and evidence.
248: 3. Approval creates a correction record and recalculates the daily summary using the applicable policy version.
249: 4. Rejection records the reviewer and reason and notifies the requester.
250: 5. If the payroll period is locked, the correction requires reopening or an adjustment in the next payroll period according to management policy.

301: 9.1 Leave Workflow
302: 1. Employee selects leave type and dates; the server calculates duration, holidays, balance and eligibility.
303: 2. Employee provides reason, contact during leave, handover/reliever where required and supporting evidence.
304: 3. The system routes the request according to staff category, duration, site and configured approval matrix.
305: 4. Approval reserves/deducts leave and updates attendance. Rejection records reason. Cancellation follows a separate controlled action.
306: 5. Any paid/unpaid, encashment or KPI consequence is displayed before final approval and handed to payroll with traceability.

443: 14.1 Critical Data Constraints
444: Employee ID, CNIC/passport (where applicable), official email and active mobile username must be unique.
445: Raw Punch Event is append-only. Attendance summaries may be recalculated but must retain calculation version and history.
446: More than one raw punch per employee/day is valid; therefore a unique EmployeeId plus AttendanceDate constraint must not be placed on raw events.
447: Policy, shift, assignment and compensation changes require effective dates and may not silently rewrite prior periods.
448: Files are private objects referenced by metadata; database backups alone are not a complete backup without file storage.
449: Zone events reference the exact zone version and assignment effective at event time; later boundary edits shall not rewrite historical evidence.
