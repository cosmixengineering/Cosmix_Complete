# Configurable claim and benefit approval routing

Part A adds operational configuration and a shared authorization contract. It preserves the existing fixed Admin hiring/status/ordinary-leave and HR correction/overtime workflows. No routes, roles, grants, payment approvals, amounts or delegation defaults are seeded.

`GET/POST /api/v1/approvals/routes` reads/publishes immutable route versions. Publication requires a current web MFA session and explicit All-scope `approvals.routes.manage` plus All-scope authority for the selected stage's review permission. Admin and HR accounts can publish when explicitly granted this authority; no fixed system role or automatic grant is required. The only review permissions are registered `approvals.stages.1.review` through `approvals.stages.20.review`; `ApproverPermission` must exactly match `Stage`. `ApprovalPermissions.Review` is a source-code alias for stage 1. The old `approvals.requests.review` string is unsupported and confers no authority. Read requires `approvals.routes.read`. Each code identifies one stage/filter rule; its next version must name the expected current version and start after the prior version. Retroactive publication is refused. A successor supersedes the old code from its start date; expiration never revives the older version. Codes for different stages are separate. Staged configuration remains unusable until a unique contiguous chain starting at stage 1 matches a subject.

Use the existing fixed-administrator role configuration APIs to assign each required stage permission explicitly to the confirmed role and scope. Possession of a stage-1 permission does not authorize stage 2; a role can receive multiple stage permissions only through separate explicit grants. Role configuration requires current fixed administration and All-scope `access.roles.permissions.manage`; the administrator does not need to personally own the business permission being configured. There are no seeded approver roles or stage grants. Resolver validation rejects unsupported or mismatched stage permissions even if malformed configuration is supplied outside publication. The selected permission remains part of the immutable rule, route fingerprint and protected publication evidence.

Supported extension request types are `allowance`, `fuel`, `vehicle-maintenance`, `leave-encashment`, `advance`, `loan` and `policy-exception`. Confirm each real authority matrix before publishing it. Existing fixed workflow names are refused. Amount, currency, duration, category, department, site and risk filters use persisted subject values; no priority fallback selects between overlapping matches. Published amount bounds must be nonnegative, at most `9999999999999999.99`, and supplied with at most two fractional decimal places, matching SQL `decimal(18,2)`. Additional fractional places are rejected, including trailing zeros; amounts are never rounded. Invalid bounds are rejected before any rule, receipt, audit or private evidence is staged. Missing, ambiguous or incomplete routes return a readiness conflict.

`GET/POST /api/v1/approvals/delegations` lists the current actor's grants or delegates authority the actor actually holds. `POST /api/v1/approvals/delegations/{id}/revoke` revokes the actor's own delegation with reason and SQL rowversion. These administration endpoints require current web MFA and explicit All-scope `approvals.delegations.manage`; the delegated stage review permission can be scoped. Permission/scope are recorded on the delegation itself and must match the selected rule at decision time. A stage-1 delegation does not authorize stage 2. Future finite windows are allowed. Self delegation, widening beyond current authority and overlapping identical delegation windows are refused. Revocation can cancel a future window. Old records lacking permission/scope confer no authority. Grant evidence is immutable and cannot be deleted.

All writes require `Idempotency-Key` (8–100 allowed ASCII characters). Actor/action/key and payload fingerprint are retained with a protected result for 24 hours in the existing serializable authentication transaction. Identical retries return the original result after current authorization; changed payload conflicts. Private storage errors abort the transaction. Replay metadata can describe the original result; use the read API for current revoked state.

Developer 2/claim-benefit consumers must call `IApprovalRouteResolver` with server-resolved subject/calculation values at submission, freeze the entire subject snapshot, ordered rule IDs/versions and route fingerprint in protected evidence, and create one `ApprovalRequest` for the first stage. At every stage, inside the same authorization/business transaction, re-read unchanged subject values, validate all prior stage decisions, and call `IApprovalAuthority.RequireAsync` with the frozen fingerprint/current rule. Requester and beneficiary self review are denied both directly and through the delegator. Delegation permission/scope, source account/employment and current underlying grants are revalidated at decision time. Persist the returned role assignment/delegation/rule versions with the reason and protected before/after values using the existing `ApprovalDecision`/audit history. Only the final approved stage may materialize the consumer's effect. This component itself does not alter a claim, pay money or decide a benefit; consumers are the later D/E implementation work.

SQL schema additions are coordinated in the new Part A migration. No database/provider writes are performed by this implementation. Offline/service checks are recorded in the Part A result, and genuine authenticated SQL concurrency, rollback/restart and complete D/E request-stage acceptance remain required before deployment signoff.
