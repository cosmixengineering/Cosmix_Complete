STORAGE SIZING METHOD AND LIMITATIONS
Public registry JSON was read from this Windows workstation. The five image
manifests contain 53 unique layer digests after deduplication.
Only four-byte gzip trailers were fetched for those layers using bounded HTTP
206 range responses (212 bytes of layer payload total); no full image/model
payload was downloaded, and nothing was downloaded to the Ubuntu server.
All 53 trailer checks succeeded. ISIZE measures gzip payload size modulo 4 GiB;
the sum is a sizing estimate/lower-bound signal, not an extraction benchmark.
Tar padding, filesystem allocation, metadata and any 4-GiB wrap can affect actual
disk use. A complete image extraction has NOT been tested.
Unique compressed layers: 2,265,065,644 bytes.
Sum of trailer uncompressed-tar sizes modulo 4 GiB: 5,069,465,088 bytes.
Combined sizing estimate: 7,334,530,732 bytes (6.831 GiB).
Docker documentation confirms this containerd store retains compressed layers
and extracts them; compressed-download size alone would understate disk use.
Estimated remaining space: 1,015,349,588 bytes (0.946 GiB).
This excludes the database, container writable layers, logs, any runtime model
downloads, ONNX Runtime/models, and OS/update capacity.
Preflight reserve proposal: at least 3 GiB beyond this image estimate for an
initial isolated trial. This is an engineering guard, not a vendor minimum or
a validated production storage budget. Current capacity fails that guard.
