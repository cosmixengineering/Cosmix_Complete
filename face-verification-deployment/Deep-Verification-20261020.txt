Confirmed defects and fixes
--------------------------
1. Ordinary capture rejection was classified as provider outage.
   CompreFace 1.2.0 HTTP400/code28 and31, valid empty/multiple detection results,
   and valid low-confidence detection now remain ordinary rejection. They cannot
   pass identity/liveness. Wrong/missing credentials, unknown errors, malformed
   JSON/schema/coordinates/scores, redirects and transport faults stay unavailable.
   Remote error messages are not echoed. Production adapter response limits,
   duplicate-key rejection and private-CA/destination checks remain enforced.
   Initial RED: 15 failing assertions. Added mixed low-confidence + malformed
   comparison regressions exposed six more failures; the complete comparison
   schema, score and source/target bounds are now validated before applying the
   low-confidence classification. Independent re-review found no new defect.

2. A saved successful verification receipt retained CanSubmitCheckIn=true after
   the proof had expired/been consumed or the enrollment/configuration changed.
   Replays now preserve their historical outcome/reason/expiry/version while
   recomputing current submission eligibility under fresh session/device and
   permission checks. Both early receipt replay and final concurrent receipt
   reconciliation receive this check. A final clock check covers expiry during
   authorization/audit. Check In still independently validates/consumes proof.
   RED: eight stale-readiness scenarios failed; an extra authorization-time expiry
   regression also failed before its fix. Updated application fixture:180 pass.

3. Provider-disabled capture configuration could select the raw encrypted vault
   without the retention controller, although capture upload could remain enabled.
   Storage selection now always applies the retention controller. Missing policy/
   journal, untracked objects and expired use permission fail closed independently
   of provider selection. The approved configured path remains usable.
   RED:3 pass/18 fail. GREEN:21 pass/0 fail with real private TEMP encryption.

Remaining gaps and acceptance limits
------------------------------------
Before operational attendance acceptance:
  A. Enroll a consenting real employee using the real authorized session/device.
     Test genuine camera, other person, no/multiple face, print, phone-screen/video
     replay, blur/dark/backlight, reconnect/timeouts, enrollment replacement and
     revocation, exact proof expiry and duplicate Check In against real SQL.
     The initial .85 match/.90 detection/.90 per-model liveness thresholds are
     owner-delegated starting settings; they have no measured FAR/FRR here.
  B. Mock transaction fixtures do not prove SQL rollback/locking/crash recovery,
     particularly failure after prior enrollment revocation during replacement.
  C. Concurrent verify requests before a receipt exists can repeat inference;
     finalization/proof consumption stay single-use. The app should serialize
     unresolved verify requests. Server exactly-once execution/load acceptance
     remains unproven, and rate/concurrency capacity requires measurement.
  D. Configuration capability does not read enrollment storage-use metadata.
     At storage-use expiry, an active enrollment can still report configuration
     readiness; verify rejects with face_evidence_use_expired and can leave the
     challenge Pending. The client needs explicit expiry/re-enrollment handling;
     a richer metadata eligibility contract is a future backend improvement.
  E. Storage use expiry denies reads; physical deletion/orphan cleanup, backup/key
     retention and full data restore have not been enabled/accepted. Ciphertext
     is not claimed to be erased at120sec/90days.
  F. Added tests cover queue cancellation and concurrent native calls, not every
     running-native cancellation/disposal race. Crop/tensor expected values pass;
     full spatial resize parity with an upstream golden output remains unproven.
     One malformed PNG codec case passes; this is not a complete codec corpus.
  G. API is a local developer process, not supervised Ubuntu ERP hosting. Phone
     networking, certificate deployment, restart supervision, backup/restore and
     concurrent load testing remain needed. Ubuntu has about5.3GiB RAM/no swap;
     no capacity guarantee is made by these sequential/small mock runs.
