## Concrete Defects

Priority here is operational triage: P1 should block release of the affected workflow; P2 is a material correctness/integration defect. Findings are established by static paths and still need runtime validation after the backend build is fixed.

### PS-01 [P1] New service APIs omit business permissions and ownership

A valid signed-in tenant user can enter job creation/assignment/start/completion, complaint assignment/resolution, ticket status changes and delivery confirmation without a named service permission. Lists and GUID detail lookups also omit customer/employee ownership. This permits unrelated users to read or alter other same-tenant service records if the endpoints are made runnable. Authentication-only API keys also do not reach the permission-scope handler. Evidence: `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:15`, `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:94`, `src/NOIR.Web/Endpoints/ComplaintEndpoints.cs:89`, `src/NOIR.Web/Endpoints/TicketEndpoints.cs:56`, `src/NOIR.Web/Endpoints/FulfillmentEndpoints.cs:57`, `src/NOIR.Infrastructure/Identity/Authorization/PermissionAuthorizationHandler.cs:35`. SRS: ROLE-001/003 and CUS01/CUS07 (`../analysis/hr_srs.txt:202`, `../analysis/detailed_srs.txt:1781`).

### PS-02 [P1] Customer OTP is caller-chosen, disclosed, optional and reusable

Creation accepts `CustomerOtp`, copies it to a public entity property, and returns the entity. GET also returns entities containing the plaintext value. An omitted/empty stored OTP disables verification entirely; a nonempty value has no expiry, failed-attempt budget or consumed state. Repeating confirmation can reuse it. This does not prove recipient identity or a customer-controlled SMS response. Evidence: `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:70`, `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:76`, `src/NOIR.Domain/Entities/Fsm/FieldJob.cs:27`, `src/NOIR.Domain/Entities/Fsm/FieldJob.cs:85`, `src/NOIR.Web/Endpoints/FulfillmentEndpoints.cs:39`, `src/NOIR.Web/Endpoints/FulfillmentEndpoints.cs:23`, `src/NOIR.Domain/Entities/Fulfillment/DeliveryChallan.cs:26`, `src/NOIR.Domain/Entities/Fulfillment/DeliveryChallan.cs:75`. JSON options omit nulls, not OTP properties (`src/NOIR.Web/Program.cs:120`). SRS: original delivery OTP and HR plaintext-token prohibition (`../analysis/original_srs.txt:745`, `../analysis/hr_srs.txt:558`). Applicability of OTP may be configured, but no explicit applicability policy or alternative approval gate exists here.

### PS-03 [P1] Jobs and deliveries accept invalid transitions and rewrite completion evidence

`StartJob()` unconditionally sets InProgress and StartedAt, including after completion; `CompleteJob()` can complete an unstarted/unassigned job and resets CompletedAt on each call. `ConfirmDelivery()` can move a newly created Draft straight to Delivered, without dispatched state, OTP when absent, or proof; retry changes delivery time and can replace proof. Evidence: `src/NOIR.Domain/Entities/Fsm/FieldJob.cs:77`, `src/NOIR.Domain/Entities/Fsm/FieldJob.cs:83`, `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:107`, `src/NOIR.Domain/Entities/Fulfillment/DeliveryChallan.cs:57`, `src/NOIR.Domain/Entities/Fulfillment/DeliveryChallan.cs:73`, `src/NOIR.Web/Endpoints/FulfillmentEndpoints.cs:62`. Required authorization, evidence and controlled execution are missing even where the detailed state's exact label remains a proposal (`../analysis/detailed_srs.txt:1043`, `../analysis/detailed_srs.txt:1091`).

### PS-04 [P1] Helpdesk requester and comment identity can be forged

The API trusts `CreateTicketRequest.UserId` and `AddTicketCommentRequest.UserId`, passes them directly into the domain, and never derives them from authenticated identity. A signed-in caller can attribute a ticket/comment to a different or nonexistent user. Generic audit actor and the displayed author can therefore disagree. Evidence: `src/NOIR.Web/Endpoints/TicketEndpoints.cs:36`, `src/NOIR.Web/Endpoints/TicketEndpoints.cs:49`, `src/NOIR.Web/Endpoints/TicketEndpoints.cs:73`, `src/NOIR.Domain/Entities/Helpdesk/Ticket.cs:83`. Required employee linkage and traceable support history: `../analysis/original_srs.txt:908`, `../analysis/original_srs.txt:915`.

### PS-05 [P1] Employee activation bypasses the HR v1.2 lifecycle

The factory creates Active employees immediately; the create handler validates directory fields then persists without Draft, submission, required documents, face enrollment or independent approval. The status enum has no Draft/Pending Approval/Retired, and its Suspended value has no status-change route. Base behavior is intentional in existing tests, but conflicts with the newer HR SRS. Evidence: `src/NOIR.Domain/Entities/Hr/Employee.cs:70`, `src/NOIR.Domain/Enums/EmployeeStatus.cs:6`, `src/NOIR.Application/Features/Hr/Commands/CreateEmployee/CreateEmployeeCommandHandler.cs:80`, `src/NOIR.Web/Endpoints/EmployeeEndpoints.cs:169`, `tests/NOIR.Domain.UnitTests/Entities/Hr/EmployeeTests.cs:83`. Requirements: HR-001/002/008 (`../analysis/hr_srs.txt:268`, `../analysis/hr_srs.txt:275`). This is a v1.2 adoption gap, not evidence that the inherited CRUD tests were incorrectly authored.

### PS-06 [P1] HR termination does not disable or revoke the linked account

Deactivation updates employee status/end date and reporting links, then saves. It neither disables the linked ApplicationUser nor revokes sessions; the deactivation event has a webhook mapping but no identified local account-revocation handler. Login checks the user account's IsActive rather than the linked employee's status. A terminated employee whose user account remains active can still authenticate. Evidence: `src/NOIR.Application/Features/Hr/Commands/DeactivateEmployee/DeactivateEmployeeCommandHandler.cs:37`, `src/NOIR.Domain/Entities/Hr/Employee.cs:157`, `src/NOIR.Application/Features/Webhooks/WebhookEventTypeRegistry.cs:97`, `src/NOIR.Application/Features/Auth/Commands/Login/LoginCommandHandler.cs:121`. The generic revoke-all capability exists but is not called by HR offboarding (`src/NOIR.Infrastructure/Identity/RefreshTokenService.cs:214`). Requirements: HR-005/AUTH-007/AC-009 (`../analysis/hr_srs.txt:272`, `../analysis/hr_srs.txt:226`, `../analysis/hr_srs.txt:590`). No attendance endpoint exists to demonstrate a post-termination punch.

### PS-07 [P2] Delivery quantities and service references lack business validation

Challan creation can contain no items or nonpositive quantities; AddItem/constructor simply copy input, and quantity configuration sets precision only. FSM/complaint assignment accepts any technician GUID without checking active employee, skill, certification, site or availability. Customer/project/product references are copied without scoped existence checks in these paths. Evidence: `src/NOIR.Web/Endpoints/FulfillmentEndpoints.cs:42`, `src/NOIR.Domain/Entities/Fulfillment/DeliveryChallanItem.cs:19`, `src/NOIR.Infrastructure/Persistence/Configurations/FulfillmentAndStoresConfigurations.cs:35`, `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:86`, `src/NOIR.Web/Endpoints/ComplaintEndpoints.cs:81`, `src/NOIR.Infrastructure/Persistence/Configurations/FieldJobConfiguration.cs:51`. This allows invalid/dangling business associations in the inspected model; a cross-tenant data disclosure is not asserted. Required validation/eligibility: `../analysis/detailed_srs.txt:1050`, `../analysis/detailed_srs.txt:1075`.

### PS-08 [P2] Service module toggles are not enforced on their APIs

FSM, complaints, helpdesk and fulfillment are declared toggleable, yet their endpoint groups omit `RequireFeature` and directly execute DbContext operations instead of feature-gated message handlers. Disabling a module therefore has no identified server gate on these routes. Evidence: `src/NOIR.Application/Modules/Erp/FsmModuleDefinition.cs:10`, `src/NOIR.Application/Modules/Erp/ComplaintsModuleDefinition.cs:10`, `src/NOIR.Application/Modules/Erp/HelpdeskModuleDefinition.cs:10`, `src/NOIR.Application/Modules/Erp/FulfillmentModuleDefinition.cs:10`, `src/NOIR.Web/Endpoints/FieldJobEndpoints.cs:13`, `src/NOIR.Web/Endpoints/ComplaintEndpoints.cs:13`, `src/NOIR.Web/Endpoints/TicketEndpoints.cs:9`, `src/NOIR.Web/Endpoints/FulfillmentEndpoints.cs:10`. Existing gate implementation is explicit, not automatic (`src/NOIR.Web/Filters/RequireFeatureFilter.cs:45`); base HR uses it (`src/NOIR.Web/Endpoints/EmployeeEndpoints.cs:30`).

### PS-09 [P2] Service navigation has no rendered destination

Sidebar links target FSM jobs, complaints, challans and helpdesk tickets, but App.tsx declares none of those routes and redirects unmatched paths to `/`. No service API client/page wiring was found. Evidence: `src/NOIR.Web/frontend/src/components/portal/Sidebar.tsx:232`, `src/NOIR.Web/frontend/src/components/portal/Sidebar.tsx:239`, `src/NOIR.Web/frontend/src/components/portal/Sidebar.tsx:254`, `src/NOIR.Web/frontend/src/components/portal/Sidebar.tsx:291`, `src/NOIR.Web/frontend/src/App.tsx:233`. Passing TypeScript/Vite compilation does not test navigation or make these workflows usable.

### PS-10 [P2] Support state changes lose the meaning of closure

Ticket status can move freely from Closed back to Open/InProgress, while ClosedAt remains set; closing again overwrites it. There is no resolution evidence or controlled reopen decision. Complaint assignment similarly overwrites Resolved with Assigned while retaining prior ResolutionNotes/ResolvedAt; resolve can also run from any state. Evidence: `src/NOIR.Domain/Entities/Helpdesk/Ticket.cs:69`, `src/NOIR.Web/Endpoints/TicketEndpoints.cs:61`, `src/NOIR.Domain/Entities/Complaints/CustomerComplaint.cs:53`, `src/NOIR.Domain/Entities/Complaints/CustomerComplaint.cs:59`. Required history/closure review: `../analysis/detailed_srs.txt:805`, `../analysis/detailed_srs.txt:1123`.

### PS-11 [P2] Expected OTP rejection becomes a server error

Wrong nonempty OTP throws InvalidOperationException from FieldJob/DeliveryChallan. Endpoints do not map it to a validation result, and the global exception switch sends unrecognized exceptions to the 500 handler. Evidence: `src/NOIR.Domain/Entities/Fsm/FieldJob.cs:85`, `src/NOIR.Domain/Entities/Fulfillment/DeliveryChallan.cs:75`, `src/NOIR.Web/Middleware/ExceptionHandlingMiddleware.cs:70`, `src/NOIR.Web/Middleware/ExceptionHandlingMiddleware.cs:272`. A customer input error should have a clear rejected result rather than appear as provider/server failure (`../analysis/detailed_srs.txt:1047`).
